# OneLive 创新大赛演示台设计说明

日期：2026-08-17
状态：已评审通过，待转实施计划

## 1. 目标

为创新大赛现场演示打造一个前端：让评委在 3 分钟内看懂 OneLive 的根技术突破、看见它对网络流量的真实需求、并自行得出商业价值判断。

做法是把两份已有资产合成一个：以我方 `demo/index.html` 的播控台为底座（视觉、骨架、逐帧真算劣化引擎），装入队友 PR #1 的内容（四段真实电商成片、本地化叙事、能力边界标注）。

产出仍是**单文件、双击即开、断网可演**。

## 2. 已决策项

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 真实性档位 | 纯前端，全部预生成，不启后端 | 零故障风险；真实性由逐帧真算的劣化 + 可追溯的实测证据承担 |
| 代码底座 | 我方 `demo/index.html` | 视觉与播控骨架明显更强；带宽账本是现成的流量叙事装置 |
| 内容来源 | 队友 PR #1 | 四段成片是真实电商带货，场景与服装整体本地化，商业价值自明 |
| 根技术主线 | 生成式本地化下沉到端侧 | 唯一能推出"主播侧 N 路并发上行"的拓扑，直接对上运营商价值 |
| 画幅 | 版面容器改 9:16 竖屏 | 素材不被裁；四竖屏窗更像真实手机直播监看；两侧留白正好放文案与指标 |
| 拓扑开关形态 | 左栏普通分段控件，不做视觉强调 | 分量由切换后满屏数字联动体现，不靠视觉喊 |
| 商业价值呈现 | 不设"商业账本"，只显示平台流量数据 | 评委自己算这笔账比我们贴宣传板有力 |

明确不采用：参数化传输（传驱动系数而非像素）。它的卖点是省流量，与赛题要的"创造流量需求"相反，且当前代码传的是 JPEG 帧，讲了即失实。可在附录主动说明这一取舍。

## 3. 根技术叙事

**突破点**：数字人生成从离线渲染变为流式实时驱动（单张照片即可驱动，无需建模训练）；本地化从整段批处理变为段级流水线（ASR → 翻译 → TTS → 口型逐段吐出，双超时兜底）。两者合起来，把原本必须放在数据中心的多语言分身生成，压进了端侧与近端边缘的算力包络。

**原本解决不了的问题**：跨境直播只有两条路——每个市场配本地主播（成本与排期 ×N，人设不统一），或单路回传中心云做本地化（跨洲往返使音画错位不可控，主播无法与观众实时互动）。

**网络价值**：只有端侧生成拓扑会在主播侧形成 N 路并发上行。上行是移动网最稀缺的方向，且这 N 路对时延抖动极敏感——既拉动上行流量，又天然创造 QoD 差异化保障的付费理由。市场数从 3 扩到 10，上行需求线性增长。

## 5. 数字模型

### 5.1 现有量（不改）

```
LADDER    1080P 6.00 / 720P 3.00 / 480P 1.20 / 360P 0.70 / 240P 0.35  (Mbps)
AUDIO     0.16 Mbps 每路
perLane   = 画质码率 + AUDIO
NETS      优秀 5G SA  cap 8.25  rtt 35   jit 0
          良好 5G NSA cap 4.10  rtt 78   jit 35
          拥塞 4G     cap 1.45  rtt 180  jit 100
          弱覆盖 4G边缘 cap 0.42 rtt 420  jit 240
chN       = 在播语言频道数（本演示为 3）
plN       = 已开启平台数
egress    = chN × plN × perLane
```

`egress` 是分发侧（出口）需求，与拓扑无关——两种拓扑最终都要向同样多的市场与平台交付。拓扑只改变**上行**侧。

### 5.2 新增：拓扑

现有代码 `uplink = perLane`（上行恒为 1 路）本身就是云端拓扑。拓扑开关只把这一行变成可切换：

```
uplinkNeed = (topo === 'edge' ? chN : 1) × perLane(targetQ)
capEff     = qod ? QOD_GUARANTEE[net.m] : net.cap
ABR        : 自 targetQ 起逐级降档，直到 (topo==='edge' ? chN : 1) × perLane(q) ≤ capEff
uplinkReal = (topo === 'edge' ? chN : 1) × perLane(actualQ)
缺口        = capEff − uplinkNeed        // 可为负，负值即触发 ABR 的原因
余量        = capEff − uplinkReal
```

带宽账本必须同时显示 `uplinkNeed`、`capEff`、缺口、`uplinkReal`。只显示余量会让缺口永远为正（ABR 已经把它压下去了），戏剧性和论证都会丢失。

### 5.3 新增：QoD

QoD 不凭空创造带宽，它依赖底层接入制式提供的保障能力：

```
QOD_GUARANTEE = { '5G SA': 22.0, '5G NSA': 12.0 }
4G 档位（拥塞 / 弱覆盖）：开关灰置，提示「当前接入制式不支持 QoD 保障」
```

### 5.4 新增：时延与音画同步

```
E2E_edge  = net.rtt + 端侧本地化推理 180
E2E_cloud = net.rtt + 跨洲往返 250 + 云端本地化推理 420 + 分发 155
avSkew    = AV_BASE[topo] + net.jit × 0.6      // AV_BASE: edge 40, cloud 440
```

音画错位的成因表述固定为：高 RTT 本身不必然造成错位，错位来自视频路径与语音链路（ASR / 翻译 / TTS）的处理与回传延迟不一致。端侧的段级流水线把这个差值压到 40ms 量级。

### 5.5 三段式实算结果

链路固定「优秀 5G SA 8.25」，目标画质 1080P，三路语言：

| 状态 | 目标需求 | 容量 | 缺口 | ABR | 实际上行 | E2E | A/V |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 云端生成 | 1 × 6.16 = 6.16 | 8.25 | +2.09 | 1080P | 6.16 | 860ms | 错位 440ms |
| 端侧生成 | 3 × 6.16 = 18.48 | 8.25 | −10.23 | 降至 480P | 4.08 | 215ms | 同步 40ms |
| 端侧 + QoD | 3 × 6.16 = 18.48 | 22.00 | +3.52 | 1080P | 18.48 | 215ms | 同步 40ms |

端侧那一行的降级链：18.48 > 8.25 → 720P 仍 9.48 > 8.25 → 480P 得 4.08 ≤ 8.25 成立。

## 6. 演示动线

全程链路固定「优秀」，只动生成位置与 QoD 两个开关。

1. **开播** — 点「开始直播」，手机上行 LIVE，三路市场依次上线，链路逐段点亮，五平台开始推流。评委看到一个中国主播说中文，四窗同屏播出原片与日语和服版、西语版、印度英语版，场景与服装都换了。
2. **本地化深度** — PROGRAM 切日语版，左栏显示中日文案逐条对照。评委看到这不是加字幕，是整条内容的重制。
3. **拧网络** — 链路切「拥塞」，画面按丢包真丢帧、按带宽真降采样、按抖动真延迟绘制，画质自动降级并告警。这一步建立"网络是瓶颈"且"劣化是真的"，让后续所有网络论证可信。切回「优秀」。
4. **切拓扑（转折点）** — 生成位置由云端切端侧。上行需求 6.16 → 18.48，缺口 +2.09 → −10.23，ABR 强制降至 480P；同时 E2E 860 → 215ms，音画错位 440 → 40ms，**PROGRAM 音频延迟真实归零，评委能听出声音瞬间对齐**。结论由评委自己得出：云端省上行但跨洲回传让音画错位到无法互动；端侧能实时同步，代价是上行翻三倍而链路吃不下。
5. **开 QoD（闭环）** — 保障容量 8.25 → 22，18.48 装得下，画质弹回 1080P 且同步保持。既要实时又要画质，唯一的解是网络侧给出确定性保障。
6. **加平台** — 逐个打开五平台，出口 = 语言数 × 平台数 × perLane，平台流量表同步增长。3 语言 × 5 平台 = 15 路出口；市场扩到 10 个，上行需求即 61.6 Mbps。

## 7. 素材接入

来源 `pr-1:public/demo-media/`，实测规格：

| 素材 | 分辨率 | 时长 | 视频 | 音频 |
| --- | --- | --- | --- | --- |
| original-zh | 1080×1920 | 14.4s | h264 60fps | aac 44.1k 立体声 |
| japan-ja | 720×1280 | 15.0s | h264 60fps | aac 44.1k 立体声 |
| latam-es | 720×1280 | 15.0s | h264 60fps | aac 44.1k 立体声 |
| india-en | 720×1280 | 15.0s | h264 60fps | aac 44.1k 立体声 |

映射到 `demo/assets/`：original-zh → CAM，japan-ja → CH1，latam-es → CH2，india-en → CH3。同名 JPG 作 poster。

四段素材均为 9:16 竖屏，MULTIVIEW 与 PROGRAM 容器改为 9:16。PROGRAM 区域右半留白承载本地化文案对照与指标条。

**音频策略**：仅 PROGRAM 所选那一路出声，其余静音。四路同响会互相打架，且现场只需听当前讲解的一路。

**音画错位的实现方式（已实测定案）**：不采用队友的 `createMediaElementAudioDelay`。实测证明 `file://` 下 Chrome 对本地媒体的 `createMediaElementSource` 输出全零并报 `MediaElementAudioSource outputs zeroes due to CORS access restrictions`——WebAudio 路线与"双击即开"的交付方式不可兼得。

改用**双元素偏移**：四个 `<video>` 全部保持 `muted` 只负责画面（沿用现有 canvas 渲染管线），另设单个 `<audio id="pgmAudio">` 承载 PROGRAM 那一路的声音，令

```
pgmAudio.currentTime ≈ pgmVideo.currentTime − avSkew/1000
```

已实测：`file://` 下 audio 元素可正常出声、`currentTime` 正常推进、偏移可控。对齐采用 `playbackRate` 微调（偏差 > 80ms 时置 0.97/1.03 牵引，偏差 > 400ms 才硬 seek），避免频繁赋值 `currentTime` 产生跳音。播放由「开始直播」点击手势触发，满足自动播放策略。

该方案还比 WebAudio 更贴合叙事方向：语音链路（ASR/翻译/TTS）处理更长 → 声音晚于画面，正是 `audio` 落后 `video` 的形态。

## 9. 诚实边界

页脚常驻声明：成片为预生成素材；网络参数、Edge、QoD、时延数值为可控模拟，不代表生产部署或商用 SLA。

证据抽屉（默认收起，评委质疑时拉开）列出 M0–M4 实测，每条标注来源文件：真实 RTMP 推出 h264/aac 直播流、推流端被杀 1.3s 检出 / 10.3s 恢复、clumsy 内核级丢包损伤、WS ping/pong 实测 RTT、引擎 E2E 延迟中位 674ms、171 个 Python 测试。

界面上不得把预置文案描述为实时 AI 翻译；不得把模拟指标标为 LIVE。

## 10. 验收与回退

**验收**
- 动线走查：playwright 于 1440×900 逐步截图，六步各一张，人工核对无裁切、无重叠、无溢出
- 数字自洽：断言 §5.5 三段式表格每个数字（目标需求 / 容量 / 缺口 / ABR 结果 / 实际上行 / E2E / A-V）
- 音频：断言仅 PROGRAM 路出声（四个 video 恒为 muted，仅 `#pgmAudio` 不静音）；断言云端拓扑下 `video.currentTime − pgmAudio.currentTime` 收敛到 0.44s±0.12、端侧收敛到 0.04s±0.12
- 离线：断网并以 `file://` 双击打开，确认四段视频与音频均可播放
- 视觉尺寸：1440×900 与 1920×1080 首屏完整

**回退**
- 现有占位素材备份保留
- `topo` 默认 `cloud`、`qod` 默认关；新开关一个都不碰时，退化为当前已能演示的版本
- 保留现有 `demo/README.md` 的现场动线说明并同步更新
