# OneLive Future Experience V2 设计稿

## 1. 为什么重做

V1 虽然可操作，但评委看到的仍然是一张竖屏视频经过三次裁切：

- 主播、商品、面部三个视图没有新的观察信息，不能证明多视角。
- 空间模式只是把竖屏平面旋转，像一张悬空海报，不像空间资产。
- 55.44 Mbps 等数字集中在右侧说明区，与画面变化脱节。
- 面板和小字过多，第一眼仍然是控制台，而不是未来体验。

V2 的目标不是堆更多指标，而是让评委先看到新的观看方式，再自然理解为什么需要 Edge、按需视口和 QoD。

## 2. 核心叙事

### 多视角

同一直播时刻由三个语义明确的镜位共同表达：

1. 正面主播：人物、表情和完整商品关系。
2. 侧面互动：新的横向视差、台面深度和主播手势。
3. 俯拍商品：商品结构、锅内细节和操作动作。

这三路不是前端裁切，而是 AI 生成的同步镜位关键帧。当前版本用关键帧做稳定预演，未来可无缝替换为同步循环视频。

### 空间直播

从三机位继续向前，画面进入空间重建视图：中央主体保持真实，环境边缘逐渐显现深度采样和空间点云。用户拖动时不是旋转一张卡片，而是改变观察窗口，背景、主体和前景产生不同位移。

当前仍是 2.5D 概念预演，不声称已经完成实时三维重建。

## 3. 界面结构

V2 使用全屏演播室展映层，不再采用“左侧小舞台 + 右侧长说明卡”的普通弹窗结构。

```text
┌────────────────────────────────────────────────────────────────────┐
│ OneLive ViewLab       多视角 / 空间直播       概念预演        关闭 │
├──────────────────────────────────────────────────┬─────────────────┤
│                                                  │ 当前叙事        │
│                                                  │                 │
│                 16:9 主展映舞台                  │ 3 × 3 交付矩阵  │
│                                                  │ 或当前视口说明  │
│                                                  │                 │
│  正面主播     侧面互动     俯拍商品              │ 网络能力链      │
├──────────────────────────────────────────────────┴─────────────────┤
│  全量同步  9路 / 55.44M         当前视角优先  3路 / 18.48M       │
└────────────────────────────────────────────────────────────────────┘
```

布局原则：

- 主展映舞台占可用面积约 72%，画面而不是指标成为视觉中心。
- 右侧只保留当前动作所需的信息，不重复解释所有技术。
- 三个镜位使用横向导演条，不使用三个等大的信息卡。
- 网络策略放在舞台下方，切换后画面和交付矩阵同步变化。
- 全局只使用 OneLive 青蓝作为交互强调色；琥珀仅表示容量不足。

## 4. 多视角模式

### 主舞台

- 使用 16:9 AI 关键帧填满舞台。
- 视图切换采用 240ms 交叉淡化和轻微推镜。
- 左上显示功能性机位名称，不覆盖装饰标签。
- 右上只显示 `AI 关键帧 / 概念`，避免误认成实时生成。

### 导演条

- 三个缩略图分别对应正面主播、侧面互动、俯拍商品。
- 选中态同时使用边框、文字和位置标记，不只依赖颜色。
- 每个缩略图显示它解决的观看任务：人物表达、空间关系、商品细节。

### 交付矩阵

右侧使用 3 行语言 × 3 列视图组成九格矩阵：

- 全量同步：九格全部激活，展示 9 路 / 55.44 Mbps。
- 当前视角优先：每个语言只保留当前视图，展示 3 路 / 18.48 Mbps。
- 若当前 Demo 已开启 QoD，矩阵继续遵循两路 VIP 1080P、一路 Best Effort 480P，不把九格全部显示为高清。

矩阵让“语言数 × 视图数”直接可见，避免只读公式。

## 5. 空间直播模式

### 空间舞台

- 使用宽幅空间重建关键视觉作为完整背景。
- 拖动或滑杆改变观察角度，范围 -30° 到 +30°。
- 图像平移、缩放和边缘采样层以不同速率变化，形成 2.5D 视差。
- 不显示虚构摄像机型号，不旋转竖屏卡片。

### 右侧信息

只展示三件事：

1. 输入来自多机位或深度采集。
2. Edge 负责时空对齐、重建、渲染和视口预测。
3. 网络只交付当前视口、核心音频与交互控制。

空间模式不显示固定码率，使用“场景相关 / 按视口自适应”。

## 6. 素材生产方案

### 当前可用素材

`demo/assets/future/` 中保存四张 1600px 宽 WebP：

- `front.webp`：正面主播镜位。
- `side.webp`：35° 侧面互动镜位。
- `overhead.webp`：俯拍商品镜位。
- `spatial.webp`：空间重建关键视觉。

四张图均由现有日本频道画面作为身份、服装、商品和场景参考生成。它们用于界面原型，不代表真实多机位采集。

### 推荐最终素材

比赛终版建议生成三个 15 秒同步无声视频：

| 镜位 | 画面 | 固定要求 |
| --- | --- | --- |
| 正面主播 | 正面中广景，主播与锅完整 | 固定机位、无推拉、无切镜 |
| 侧面互动 | 主播左侧 35°，看到台面深度 | 同一动作进度、同一手势 |
| 俯拍商品 | 顶部俯拍锅具和双手 | 锅具不变形、手指稳定 |

统一技术规格：

- 1920 × 1080，30fps，15 秒，H.264，无音轨。
- 三路首帧、动作峰值和结尾对齐。
- 同一人物参考、服装参考、商品参考和运动参考。
- 不生成字幕、UI、平台标识、品牌文字或水印。
- 生成完成后先人工检查脸、手、锅具把手、电源线和背景连续性。

为了降低浏览器解码压力，建议将三路最终视频横向拼接为一个同步图集视频：

```text
multi-angle-atlas.mp4
┌──────────────┬──────────────┬──────────────┐
│ 正面 960×540 │ 侧面 960×540 │ 俯拍 960×540 │
└──────────────┴──────────────┴──────────────┘
总尺寸 2880×540，15秒，30fps，单路解码
```

前端用三个 Canvas 从同一个视频裁取不同区域，可以保证绝对同步，又不会新增三个解码器。

### 视频生成提示词约束

每个镜位都应重复以下约束：

```text
同一位成年东亚女性主播，同一张脸、同一发型、同一淡紫色服装、
同一灰色电锅、同一暖色厨具展厅、同一时刻和动作进度。
固定摄像机，15秒连续镜头，无转场，无变焦，无字幕，无水印。
手指、锅具把手、电源线和台面透视必须稳定。
```

优先使用支持 reference image、reference video、character consistency、motion transfer 或固定 seed 的生成工具。三路分别生成后，不要直接投入 Demo，先统一帧率、时长和关键动作时间点。

## 7. 网络叙事

V2 不说“更多视角一定等于上传九路原视频”，而是展示两种交付策略：

- 全量同步：所有语言、所有视图长期编码和交付，规模上限是 9 路。
- 当前视角优先：Edge 只渲染或转发用户正在观看的视图，规模回到每个语言一路。

QoD 不让总带宽无限增长，只在有限预算中优先保证当前视口、声音和控制信令。

## 8. 状态与容错

- 四张未来素材成功加载：显示 `AI 关键帧 / 概念`。
- 任一素材加载失败：回退到当前 PROGRAM 画面，并显示 `同源回退 / 概念`。
- 概念层关闭时，原四路直播媒体继续播放，不重新加载。
- `V` 打开或关闭，`Esc` 关闭，焦点在关闭后返回入口。
- reduced motion 下取消推镜和视差，只保留即时状态切换。

## 9. 验收标准

- 评委不看说明，也能一眼区分三个镜位提供了不同信息。
- 点击镜位后，主舞台在 300ms 内切换并保持 16:9。
- 切换全量同步和当前视角优先时，九格矩阵与 55.44 / 18.48 Mbps 同时变化。
- 空间模式不再出现旋转竖屏卡片。
- 1440 × 900 和 1920 × 1080 首屏完整。
- 390 × 844 无横向溢出，允许概念层内部纵向滚动。
- 页面持续显示 CONCEPT / EMULATED 和能力边界。
