# OneLive V2 重构设计（真实链路版）

日期：2026-07-16
状态：已与产品负责人对齐方向，待 spec 评审

## 1. 背景与结论

现有实现分两个版本：master 为纯 Mock 演示（导演脚本驱动，"幻灯片"体验来源）；`codex/iphone-live-avatar-mvp` 分支已有真实骨架（iPhone Safari 面捕 → Socket.IO 分发 pose → 桌面三频道渲染，WebRTC 传视频）。

评估结论：**信令/会话/双端分离骨架保留；数字人渲染层与网络层推翻重做。**

与目标的四条硬鸿沟：

1. 数字人是静态 PNG + CSS 2.5D 微动 + 叠加嘴巴色块，无真人感，不可救。
2. 网络指标与退化全部 EMULATED（应用内注入 profile），无真实测量、无真实损伤。
3. 翻译为预置三语文案，语音为浏览器 TTS，非实时 AI。
4. 不推流真实平台；手机端是网页非 App。

## 2. 硬约束（已确认）

- 本地电脑为 Intel Arc 核显（无 NVIDIA 独显），32GB 内存。
- **优先本地算力**；云 GPU 仅作降级出口和"边缘节点"角色。
- 数字人形象可预置（每市场/性别/着装一张底图），但**动作、表情、口型必须由真人实时驱动**，不允许预置动画。
- 网络速率/时延等指标必须真实测量；网络退化必须真实发生（真实损伤注入），不允许预置差异。
- 真实 RTMP 推流到公开直播平台。
- 手机端为 Expo 原生 App，IPA 经 Sideloadly 侧载（iPhone）。
- 时间：2 个月以上，比赛 Demo 性质，不要求商用级。

## 3. 总体架构

```
┌─ iPhone (Expo 原生App) ──────────────────┐
│ 摄像头/麦克风采集                          │
│ WebRTC 上行（真人视频+音频）               │
│ 网络HUD：上行码率/RTT/抖动/丢包（getStats） │
└──────────────┬───────────────────────────┘
               │ WiFi/5G（clumsy 可真实注入损伤）
┌─ PC 控制台（React 前端 + Node 编排服务）───┐
│ 三频道数字人实时预览 + 双端网络HUD          │
│ 市场/性别/着装切换   Edge⇄Local 切换       │
│ 推流启停与状态                             │
└───┬──────────────────────────┬────────────┘
    │ 驱动数据+音频              │ 字幕/状态
┌─ 数字人引擎（Python，本地或边缘GPU）┐  ┌─ 实时翻译链路 ────────┐
│ 上行视频 → MediaPipe 提取驱动数据   │  │ 流式ASR → LLM翻译 →   │
│ LivePortrait：预置底图+实时动作迁移 │←─│ 各语言流式TTS          │
│ TTS 音频 → 嘴型驱动                │  └───────────────────────┘
└───┬────────────────────────────────┘
    │ 每频道 ffmpeg 合成
    ├→ RTMP → YouTube Live（英语）
    ├→ RTMP → B站（中文/测试）
    └→ RTMP → Twitch（西语）
```

核心思想：**数字人引擎是一个接口固定的独立服务**，输入=驱动数据+翻译音频，输出=各频道视频流。跑在本地（OpenVINO/DirectML）还是边缘 GPU（CUDA）只是部署位置差异——"Edge⇄Local 切换"因此成为 Demo 中一个真实可测量的环节，而不是模拟。

## 4. 组件设计

### 4.1 手机端 App（Expo / React Native）

- 采集：`react-native-vision-camera`；上行：`react-native-webrtc`（视频+音频一路推到 PC）。
- 网络 HUD：`getStats()` 1Hz 采样——上行码率、RTT、抖动、丢包、实际分辨率/帧率，实时曲线展示。
- 控制：开播/停播、前后摄切换、码率档位（自适应+手动）。
- 构建交付：EAS Build 产出 IPA → Sideloadly 侧载（用户已有流程）。
- 兜底：现有 Safari 网页采集端保留，App 出问题时现场可退回网页。
- 不做手机端面捕：驱动数据由引擎端从**收到的**上行视频提取。这样"网络差 → 上行视频差 → 数字人动作差"是真实因果链，正好是 Demo 要证明的东西；手机端也更简单。

### 4.2 PC 控制台（React + Node 编排服务）

- 保留：Socket.IO 信令、session-registry、HTTPS 自签证书方案、市场配置体系、测试基建。
- 三频道预览：订阅引擎输出流（局域网内 WebRTC 或 WS+MJPEG，Spike 定）。
- casting 控制：市场（北美/日本/西语）、性别、着装切换 → 引擎热切换底图。
- 双端网络 HUD：手机端指标（经信令上报）+ PC 端 `getStats()`，同屏时间序列。
- Edge⇄Local：一键切换引擎目标地址，切换前后帧率/处理时延真实对比。
- UI 全部重做：实现阶段用 frontend-design / ui-ux-pro-max skill 出设计，废弃现有演示导演六步脚本 UI。

### 4.3 数字人引擎（Python 独立服务）

- 输入：上行真人视频帧（driving）+ 每频道翻译后 TTS 音频流。
- 管线：MediaPipe Face Landmarker 提取表情/头部姿态 → LivePortrait 将动作实时迁移到预置人像底图；嘴部不跟随主播，改由该频道 TTS 音频 → viseme 序列 → LivePortrait 嘴型 retarget（口型对目标语言）。
- 预置形象库：3 市场 × 2 性别 × 2 着装 = 12 张高质量底图（离线生成，符合目标市场风格）。
- 部署双形态，同一 WebSocket/gRPC 接口：
  - 本地：onnxruntime（OpenVINO EP / DirectML）跑 Intel Arc。
  - 边缘：云 GPU（AutoDL 4090 级，约 ¥2/小时），CUDA/TensorRT。
- 输出：每频道视频帧 →（a）控制台预览流；（b）ffmpeg 合成推流。
- **M0 决策门（第 1 周 Spike）**：在 Arc 上实测 LivePortrait 推理帧率。
  - 单路 ≥15fps → 本地跑三路（降分辨率/分时调度）或本地一路+边缘两路；
  - 单路 <15fps → 本地保一路低帧率演示"Local 慢"，三路常驻边缘（方案 C 降级，架构不变）。

### 4.4 实时翻译链路

- ASR：faster-whisper（small/base，CPU 或 OpenVINO）流式转写中文；备选商用流式 ASR API。
- 翻译：LLM API 流式翻译至英/日/西三语。
- TTS：edge-tts（免费、流式、多语言多音色）为主选，音色与频道形象性别匹配；备选商用 TTS。
- 字幕：原文+译文下发控制台与推流画面。
- 端到端延迟预算（说话→数字人开口）：≤3 秒。
- 全链路失败时行为见 §7；**不使用预置翻译文案**。

### 4.5 推流

- 每频道独立 ffmpeg 进程：数字人视频 + TTS 音频 + 字幕层 → RTMP。
- 目标平台：YouTube Live（英）、B站（中/测试）、Twitch（西）；账号与直播权限由用户准备。
- 断流自动重连；控制台显示每路推流状态（码率/丢帧/重连次数）。
- 现场兜底：可选自建 SRS 接收端（现场外网不可控时切换，如实标注）。

### 4.6 网络测量与损伤（全真实）

- 测量：双端 WebRTC `getStats()` 真实采样，1Hz，时间序列图表；指标含上/下行码率、RTT、抖动、丢包、帧率。
- 损伤注入：**clumsy（WinDivert）**在 PC 端对上行 UDP 链路真实注入——拥塞（限速+丢包）、弱覆盖（高丢包+高抖动）、高时延（lag）。数字人卡顿、口型失步、频道降级是真实发生的。
- QoD 环节：改为**真实的本地 QoS 调度**——损伤规则对主频道端口选择性放行/提权，次频道继续受限。UI 如实标注"本地 QoS 调度演示，非运营商 QoD API"。
- Edge 环节：引擎部署位置真实切换，处理时延/帧率变化来自真实测量。
- 废弃：现有全部 EMULATED network profile、SeededPoseProvider、观众数假数据、体验评分模型。

## 5. 数据流与协议

- 信令/会话：沿用 Socket.IO（SDP/ICE/presence/控制命令），扩展：手机网络指标上报、casting 命令、引擎状态、推流状态。
- 媒体：手机→PC 为 WebRTC；PC→引擎为局域网原始帧或压缩流（Spike 定）；引擎→控制台预览为 WS/WebRTC。
- 现有 `AvatarPoseFrame` 协议保留为兼容兜底（引擎不可用时控制台可显示驱动数据可视化），不再是主链路。

## 6. 保留 / 废弃清单

| 保留 | 废弃 |
| --- | --- |
| Socket.IO 信令 + session-registry | CSS 2.5D PNG 数字人渲染 |
| 自签 HTTPS 方案 | EMULATED 网络 profile 体系 |
| 市场配置体系（扩展） | SeededPoseProvider / 预置翻译文案 |
| WebRTC 上行链路代码 | 演示导演六步脚本 |
| 测试基建（vitest/Playwright） | 观众数/平台假数据、体验评分 |

## 7. 错误处理与降级

- 引擎不可达：频道显示明确故障态（不假装正常），可一键切换 Local/Edge 另一端。
- ASR/翻译/TTS 失败：字幕链路保留已出内容+显示失败原因；该频道静音并明确标注，不回退预置文案。
- 推流断开：自动重连，控制台告警。
- 现场外网不可控：推流切自建 SRS；翻译链路切本地 whisper + 本地缓存 LLM 不可用时如实降级为"仅字幕无翻译"。
- 手机 App 异常：退回 Safari 网页采集端。

## 8. 测试策略

- 单元：协议、编排、QoS 规则逻辑（vitest）。
- 引擎契约测试：固定 driving 数据 + 音频 → 断言输出帧率/延迟达标（Python 侧 pytest 基准脚本，每里程碑回归）。
- E2E：Playwright 跑控制台核心流程。
- 真机：每个里程碑在物理 iPhone 上 smoke test（本地通过不等于 iOS 能用）。
- 演示彩排：完整走一遍"开播→三频道→损伤→QoS→Edge→恢复→真实平台可见"。

## 9. 里程碑（约 8 周）

- **M0（第 1 周）**：Spike——Arc 上 LivePortrait 基准、TTS→嘴型驱动可行性、引擎输出到浏览器预览通路。产出：本地/边缘算力分配决策。
- **M1（第 2–3 周）**：单频道端到端——手机（先网页）采集 → 引擎 → 1 个数字人实时复刻动作 → 控制台预览。
- **M2（第 4–5 周）**：三频道并行 + 翻译/TTS/口型同步 + casting 切换 + Expo App 成型并真机验证。
- **M3（第 6–7 周）**：真实推流三平台 + clumsy 损伤/QoS/Edge 切换 + 双端 HUD + 控制台 UI 按新设计打磨。
- **M4（第 8 周）**：真机全流程验证、演示彩排、RUNBOOK 与文档更新。

## 10. 风险

| 风险 | 缓解 |
| --- | --- |
| Arc 核显跑不动 LivePortrait | M0 第一周即验证；架构支持无缝切边缘 GPU |
| 嘴型 retarget 与动作迁移叠加效果差 | M0 一并验证；退路为嘴部区域跟随 TTS、其余跟随主播 |
| LivePortrait 依赖的 insightface 模型为非商用许可 | 比赛 Demo 可用；对外声明非商用，商用化需换模型 |
| 三路推理+三路 ffmpeg 挤爆本地 CPU | 推流编码用低档位；必要时推流合成也放边缘节点 |
| 公开平台直播审核/风控（AI 内容） | 画面加 AI GENERATED 标识；备 SRS 自建兜底 |
| 现场网络不可控 | 手机热点兜底；全链路有降级路径（§7） |
| 端到端 3 秒延迟不达标 | 各段延迟打点可观测，优先压 ASR 分段与 TTS 首包 |
